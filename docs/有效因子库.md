- 默认数据源：认证DuckDB。
- 研究截止日：2026-05-15（含）。
- 窗口：90日历日预热 + 126个交易日IS + 42个交易日OOS。
- 周期：在注册的5/10/20日预测周期内检验；标准run只把IS选中且经OOS验证的

- 门槛：统一IS筛选的最终候选，并且按IS方向定向后的OOS IC大于0。
- 完整588行结果、75行通过结果、摘要和哈希合同永久保存在来源run中。

本次OOS区间为2026-03-13至2026-05-15。截止日之后的数据不回填检验；它只用于冻结
组合后的真实前向观察、组合回测、净值和报告。

## IDE工作流

日常操作优先直接在IDE运行项目根目录`run_factor_workflow.py`。该文件顶部只有两个显式
代码分支：

1. `FactorWorkflow.VALIDATE_ALL_INTRADAY`：按上述固定窗口检验全部注册日内因子；
2. `FactorWorkflow.ADMIT_COMPLETED_RUN`：人工审阅后，将指定标准run写入有效因子库。

文件中故意没有全历史检验分支。命令行入口仅为自动化兼容，不承担默认路由。

## 存储设计

- `factor_library/library.json`：程序读取的唯一当前库，Git可审计；保存名称、状态、频率、
  注册周期、冻结使用周期、方向、来源run、关键IS/OOS摘要和证据哈希。
- `factor_library/current.csv`：从JSON自动导出，方便IDE/表格查看，不手工修改。
- `runs/factor_validation/<run_id>/`：一次检验的不可变全量证据，不把逐假设大表重复塞进库。
- `factor_library/legacy/`：旧Markdown记录的冻结快照，只用于比较，不参与当前读取。

设计保持最小：没有数据库服务、审批系统或复杂状态机。新增因子只有在完成标准run并经人工
确认后才显式入库；后续相关性去重、信号合成、成本和组合选择产生自己的独立证据。

### 库记录字段

`library.json`每个因子只保存当前准入摘要，不复制整套研究大表：

- 身份：`factor`、`status`、`frequency`；
- 周期匹配：`registered_horizons`仅保存允许检验的候选周期，`selected_period`保存本次
  IS选择/OOS检验周期，`approved_periods`保存下游允许使用的周期；当前标准run每个因子只
  批准一个周期。以后若要让同一因子跨周期使用，必须先产生相应周期的准入证据，不能仅凭
  `registered_horizons`扩张权限；
- 方向与日期：`direction`、`research_cutoff`、`admitted_at`；
- 血缘：`source_run`、`evidence_file`、`evidence_sha256`；
- 关键统计：IS IC/t/q，以及OOS IC、IC HAC t、OLS HAC t和有效天数。

同一因子以后再次通过时更新其当前记录并指向新run；旧检验不会塞入当前JSON，而由旧run
永久保留。因此库文件保持小且易读，历史证据仍完整。

### 入库失败关闭

`ADMIT_COMPLETED_RUN`不会相信一份孤立的通过名单。入库前必须同时满足：

1. 标准run含`passed_factors.csv`、`validation_summary.json`和`run_contract.json`；
2. 合同列出的每个文件存在且SHA-256一致；
3. 摘要通过数量、通过名称和CSV一致，CSV没有重复或非通过行；
4. 摘要含固定IS/OOS合同；
5. 通过后以原子替换方式写`library.json`，再自动导出`current.csv`。

完整策略配置将`factor_library.enforce_portfolio_periods`设为`true`后，单组合使用
`backtest.holding_period`、多子组合使用各自`sub_portfolios[].holding_period`逐因子核对
`approved_periods`；库外因子或周期不符都会在回测前失败。`default.yaml`里的旧10f观察基线
不是有效库组合，因此该门当前显式为`false`，避免把历史观察基线伪装成已准入策略。

检验入口已删除“顺便入库”能力，所以一次IDE Run只能生成研究证据或更新因子库，不能同时
完成两件事。

### 标准run文件

| 文件 | 用途 |
|---|---|
| `factor_validation_full.csv` | 全部送检因子的一行式IS/OOS统计、各门槛标签和最终原因 |
| `passed_factors.csv` | 从全量表抽出的最终通过者，列结构与全量表相同 |
| `validation_summary.json` | 数据源、预热/IS/OOS边界、漏斗计数、周期有效天数和通过名单 |
| `oos_factor_ic.json` | IS入围者的逐因子OOS原始统计 |
| `run_contract.json` | 工作流、日期角色、代码/配置/数据/因子集哈希及关键文件哈希 |
| `artifacts/` | 逐周期IS假设、层级FDR、适配性、漏斗与manifest |

run目录创建时要求不存在，避免覆盖旧证据；人工作业CSV使用UTF-8 BOM，JSON保持程序可读和
Git可审计。完整结果与当前库通过`source_run + evidence_sha256`连接。

注册池以后从588变为688时，标准检验会按运行时注册表发现全部688个因子，并把688行写入
`factor_validation_full.csv`；审阅后执行一次显式入库，会把本次所有通过者按因子名原子
upsert到当前库。因此若25个此前不存在的因子通过，25个会一起加入，旧75个保留为100个。
未通过重验不会自动退役旧记录；退役是另一项需要明确决定的治理动作，不能由一次检验暗中触发。

## 平行因子子集与策略库

有效因子库只回答“哪些因子、哪些周期已准入”，不替代组合目的。不同策略可以因为品种类别、
数量、杠杆、容量、换手或风险预算等要求，从有效库形成不同子集；这些下游要求反馈到子集选择
不属于流程倒置，因为子集仍不携带预测权重或回测结论。

所有当前子集与策略统一登记在`config/strategy_library.yaml`：

- `factor_sets`：平行、无默认优劣的命名子集；保存稳定ID、状态、因子名单、用途说明和
  `selection_context`。活跃子集的每个成员必须仍在当前有效因子库。
- `strategies`：平行策略目录；`preferred`最多一个，表示当前首选，`observing`持续参与观察，
  `archived`保留定义但不参加默认比较。
- 每个有效库策略引用一个`factor_set_id`和一份完整框架YAML。子集只决定成员，完整YAML负责
  周期分配、信号合成、品种、杠杆、风险、权重、成本和回测，避免参数双写。
- 单组合或多子组合YAML中的因子并集必须与所引用子集完全一致；周期仍逐因子核对
  `approved_periods`。

新增、修改、删减子集或策略只编辑这一目录及相应完整策略YAML，不修改入口代码。通常用
`archived`保留不再观察的对象；误录且没有历史价值的条目才直接删除。Git历史和每次组合run
保存的目录快照共同保留历史，不再增加独立状态数据库。
