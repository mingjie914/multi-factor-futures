# 历史：旧有效因子记录与75条单切分结果对比报告

> 历史报告：其中“新75有效因子”结论已撤销。该批结果只作为单切分观察证据，当前正式
> 有效因子库从0开始按恢复后的层级FDR与后置门流程重建。

## 结论

当时的单切分检验将75个因子标为通过，数量与记忆中的“79个”接近，但成员并不稳定：与旧文档广义
清单的交集只有23个，Jaccard相似度17.69%。这不是DuckDB切换使结果整体失真；主要原因是
旧清单混合了不同批次、不同身份和不同检验窗口，而本次首次把当时588个因子放入同一个
126交易日IS + 42交易日OOS的统一检验族，并在IS执行统一层级FDR、再用OOS方向一致性
收口。

“旧79”没有可复核的精确机器清单。2026-08-15版本的`docs/有效因子库.md`实际可解析出
78个唯一因子，其中核心层（生产基线6 + 已验证候选47 + 新候选21）为74个，另有4个
边缘观察项。本报告不人为补造第79个，主比较采用广义78，同时给出核心74口径。

## 差异原因判断

以下为已由代码、旧文档和结果文件直接确认的原因：

1. 旧78不是同一门槛产物，混合了四种身份；75条是当时单切分合同的通过者。
2. 旧检验多为长区间和分批检验；新检验固定为126日IS + 42日OOS。
3. 旧批次分别处理多重比较；新检验把588个因子作为同一研究族执行层级FDR，门槛更可比。
4. 当前注册池、部分因子公式、频率适配和计算硬化在旧记录后发生过变化。
5. 新检验显式匹配5/10/20日预测周期，并冻结最合适的实际使用周期；旧记录中的周期口径不完全统一。
6. 旧清单部分层次经过相关性去重，而75条位于相关性去重和组合筛选之前，阶段不同。

DuckDB不是可直接归因的主因。数据源迁移已经做过语义一致性认证，且本次没有发现“只因读取引擎
变化而改变业务数据”的证据。数据库release、代码版本和样本窗口均与旧运行不同，因此若要把某个
单因子差异严格归因给数据源，仍需在同一代码、同一日期、同一release上做Parquet/DuckDB A/B；
在现有证据下，更合理的解释是检验设计、因子族、周期选择和独立OOS共同造成成员变化。

## 使用建议

- 不得将75条单切分结果作为当前有效因子库；当前成员只能来自恢复后的正式准入run。
- 后续筛选和信号合成只读取schema v2的`factor_library/library.json`。
- 完整统计值以来源run为准；库只保存准入所需摘要和证据哈希。
- 42日OOS对20日预测周期仅有22个有效前瞻日（个别因子13个），本次方向门槛有效，但稳定性
  证据仍短。后续新增数据属于真实观察环境，不应反向扩充或重写本次研究期结论。
